# 개발 진행 문서

## 문서 목적

이 문서는 [docs/project-plan.md](/Users/tooning/spc/docs/project-plan.md:1), [docs/domain/README.md](/Users/tooning/spc/docs/domain/README.md:1), [docs/test-fixture-strategy.md](/Users/tooning/spc/docs/test-fixture-strategy.md:1)를 기준으로 실제 개발을 어떤 순서로 진행할지 정의한다.

이 문서는 아키텍처를 확정하는 문서가 아니라, 개발 진행과 검증 기준을 정리하는 문서다. 아키텍처 적합성 검증은 사용자가 수행한다는 전제를 둔다.

## 개발 원칙

- 도메인 시나리오와 fixture가 코드보다 먼저다.
- CRUD보다 회계 이벤트와 기대 숫자 검증을 우선한다.
- 원장과 재무제표 정합성을 맞춘 뒤 부가 기능을 확장한다.
- 1차는 개발 난이도가 낮은 자산군부터 구현한다.
- 1차 핵심 자산군은 `loan_receivable`이다.
- 투자자 배분은 1차에서 `pro-rata`로 제한한다.
- 현금흐름표는 1차에서 `indirect`로 제한한다.
- 모든 저장/조회 경로는 tenant-aware 해야 한다.
- 멀티테넌시는 1차 단순 구현과 향후 강한 격리 확장을 동시에 고려한다.

## 큐 또는 Redis가 필요한 부분

결론부터 말하면, 1차 MVP에서 큐와 Redis는 필수는 아니다. 다만 일부 작업은 명확히 비동기 성격이 있어, 규모가 커지면 큐가 필요해진다.

### 1차에서 꼭 필요하지 않은 이유

- 초기 핵심은 회계 정합성 검증이다.
- 우선 시나리오 수와 데이터량이 크지 않다.
- 동기 트랜잭션으로도 분개 생성과 원장 반영을 충분히 검증할 수 있다.

### 큐가 필요해질 수 있는 영역

#### 배치 결산 작업

- 월마감
- 분기마감
- 연마감
- 대량 재무제표 생성

이유:

- 시간이 오래 걸릴 수 있다.
- 재시도와 실행 이력 관리가 중요하다.
- 테넌트별 순차 실행 또는 격리가 필요할 수 있다.

#### 대량 평가 작업

- 상품별 평가 배치
- 손상 계산 배치
- 외화 재평가 배치

이유:

- 평가 입력값 수집과 계산이 분리될 수 있다.
- 실패한 계산만 재실행하고 싶을 수 있다.

#### 외부 연동 수집

- 환율 적재
- 시세 적재
- 은행 거래내역 수집
- ERP 동기화

이유:

- 네트워크 실패와 재처리가 잦다.
- 사용자 요청과 분리해 안정적으로 처리해야 한다.

### Redis가 유효한 영역

- 작업 큐 브로커
- 짧은 TTL 캐시
- 중복 실행 방지 키
- 분산 락

### Redis를 바로 쓰지 않아도 되는 영역

- 공식 원장 저장소
- 분개 영속 저장
- 마감 결과 저장
- 감사 로그 저장

이유:

- 이들은 정합성과 영속성이 핵심이라 RDB가 기준 저장소여야 한다.

### 권장 판단

- 1차: 큐와 Redis 없이 시작 가능
- 2차: 배치와 외부 연동이 붙으면 `Redis + BullMQ` 또는 `Temporal` 검토
- 원칙: 회계 원본 데이터는 절대 Redis를 source of truth로 쓰지 않는다

## 멀티테넌시 구현 기준

### 1차 선택

- 단일 DB
- 모든 주요 테이블에 `tenant_id`
- 모든 조회와 집계에 tenant 필터 강제

### 왜 이 방식을 선택하는가

- 초기 개발과 테스트 복잡도를 낮출 수 있다.
- fixture 기반 TDD를 빠르게 진행할 수 있다.
- 외부 SaaS 제품으로서 초기 운영 비용을 통제할 수 있다.

### 반드시 지켜야 하는 구현 기준

- `tenant_id` 없는 핵심 원장성 테이블을 만들지 않는다.
- repository/service 계층에서 tenant 컨텍스트를 필수 입력으로 받는다.
- 교차 테넌트 조회는 기본 금지하고, 운영 관리자 기능만 예외로 둔다.
- 파일 저장 경로와 객체 키도 tenant 기준으로 분리한다.
- 감사 로그에도 tenant 정보를 남긴다.

### 나중 확장을 위한 설계 기준

- 테이블명에 테넌트 의미를 하드코딩하지 않는다.
- connection 관리 계층과 repository 계층을 분리한다.
- 테넌트 식별과 데이터 접근 정책을 도메인 로직 바깥에서 주입 가능하게 한다.
- 마이그레이션과 시드 로직은 향후 schema/DB 분리를 고려해 작성한다.

## Relational DB 정당화

이 프로젝트에서 RDB는 선택이 아니라 사실상 기본값에 가깝다.

### 이유 1. 회계 데이터는 강한 정합성이 필요하다

- 분개 차대 일치
- 원장 반영 원자성
- 마감 상태 일관성
- 회계주체별 데이터 분리

이 요구사항은 트랜잭션과 제약 조건을 강하게 사용하는 RDB가 유리하다.

### 이유 2. 데이터 관계가 명확하게 연결된다

대표 관계:

- entity -> book
- book -> journal
- journal -> journal lines
- journal lines -> account
- journal lines -> dimensions
- product -> contract
- contract -> event

이 구조는 관계형 모델에 자연스럽다.

### 이유 3. 기준일 조회와 집계가 핵심이다

이 시스템은 다음 질의를 자주 수행한다.

- 특정 기준일 계정 잔액
- 특정 회계주체의 시산표
- 특정 상품의 lifecycle 이력
- 특정 기간 손익 집계
- 투자자별 배분 집계

이는 SQL 기반 집계와 인덱싱이 강한 RDB에 적합하다.

### 이유 4. 제약 조건을 모델에 반영할 수 있다

- foreign key
- unique constraint
- check constraint
- transaction isolation

회계 시스템은 애플리케이션 코드만 믿는 것보다 DB 레벨 제약을 함께 두는 편이 안전하다.

### 이유 5. 감사 대응과 재현성에 유리하다

- 특정 분개가 어느 이벤트에서 왔는지 추적
- 특정 기간 데이터를 다시 집계
- 마감 시점 숫자를 재검증

이 요구사항은 정규화된 관계형 저장소가 다루기 쉽다.

### NoSQL이 후순위인 이유

- 원장성 데이터는 문서 단위보다 관계 단위가 더 중요하다.
- 조인과 집계가 많다.
- 트랜잭션 경계가 명확해야 한다.
- 마감과 정정 처리에서 문서 스냅샷보다 이력과 관계가 중요하다.

### 결론

- 공식 원천 저장소는 `PostgreSQL` 같은 RDB로 간다.
- 캐시, 큐, 검색 보조 저장소가 필요해도 source of truth는 RDB다.

## SSR 정당화

여기서 SSR은 `Next.js` 기반 서버 사이드 렌더링 또는 서버 컴포넌트 중심 렌더링을 의미한다.

결론부터 말하면, 이 프로젝트에서 SSR은 필수는 아니지만 합리적인 선택이다. 다만 모든 화면에 SSR을 강제할 필요는 없다.

### SSR이 유효한 이유

#### 초기 로딩 시 필요한 기준 데이터가 많다

- 회계주체 목록
- 마감 상태
- 계정 필터
- 기준일 기본값
- 보고서 초기 조회 파라미터

업무 화면은 첫 진입 시 필요한 기준 데이터가 많아서, 서버에서 한 번에 조합해 내려주면 사용자 경험이 안정적이다.

#### 권한 기반 초기 렌더링이 편하다

- 테넌트 정보
- 사용자 권한
- 접근 가능한 보고 단위

외부 SaaS에서는 권한별 초기 화면 구성이 중요해 SSR이 자연스럽다.

#### URL 기반 조회 화면이 많다

- `/ledger?entity=...&asOf=...`
- `/trial-balance?period=...`
- `/statements/bs?entity=...&month=...`

이런 화면은 서버에서 URL 파라미터를 읽고 초기 데이터를 만들어 주기 좋다.

#### SEO보다 운영 안정성 측면에서 의미가 있다

이 프로젝트는 SEO 목적 서비스가 아니지만, SSR은 첫 화면의 데이터 일관성과 접근 통제 측면에서 가치가 있다.

### SSR이 과한 영역

- 대화형 전표 입력
- 복잡한 그리드 편집
- 긴 폼 입력
- 실시간 필터링

이 영역은 CSR이 더 자연스럽다.

### 권장 방식

- 셸, 리스트 초기 진입, 보고서 초기 화면은 SSR 또는 서버 컴포넌트 사용
- 입력 폼, 대화형 원장 탐색, 편집 화면은 CSR 사용
- 즉, `SSR + CSR 혼합`이 적절하다

### SSR을 선택하는 실무적 이유

- 외부 SaaS에서 첫 화면 권한 제어가 쉽다
- 초기 데이터 fetch를 서버에서 통합할 수 있다
- 클라이언트 번들 부담을 줄일 수 있다
- 업무형 조회 화면에 적합하다

### SSR을 선택하지 않아도 되는 경우

- 전체 앱을 완전한 내부 관리자 SPA로 밀고 싶을 때
- 초기 화면이 단순하고, 모든 데이터가 로그인 후 API 기반으로 충분히 빠를 때

### 결론

- 이 프로젝트에서는 `Next.js 기반 하이브리드 렌더링`이 가장 무난하다
- SSR은 조회/보고 초기 화면에 사용한다
- CSR은 입력/편집/상호작용 화면에 사용한다
- SSR의 목적은 SEO가 아니라 권한, 초기 데이터 조합, 운영 안정성이다

## 현재 시점의 권장 개발 순서

1. fixture 시나리오부터 완성한다.
2. fixture를 통과시키는 회계 엔진 최소 구현을 만든다.
3. 원장과 기준일 집계를 붙인다.
4. BS/PL/CF와 투자자 배분을 붙인다.
5. 이후 운영 통제와 외부 연동을 붙인다.
