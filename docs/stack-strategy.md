# 스택 전략

## 문서 목적

이 문서는 이 프로젝트의 기술 스택을 어떤 기준으로 선택할지 정의한다.

핵심 전제는 다음과 같다.

1. 1차 목표는 MVP를 가장 빠르고 가볍게 만드는 것이다.
2. 2차 목표는 확장성과 정교한 쿼리 능력을 확보하는 것이다.
3. 언제든 다음 스택으로 마이그레이션할 수 있는 상태를 유지해야 한다.

즉, 특정 프레임워크를 먼저 정하는 것이 아니라 `속도 -> 확장성 -> 마이그레이션 가능성` 순서로 스택을 평가한다.

## 스택 선택 원칙

- 프레임워크보다 도메인 계층 분리가 먼저다.
- 회계 엔진과 분개 규칙은 프레임워크에 종속되지 않아야 한다.
- DB 접근 계층은 교체 가능해야 한다.
- 집계와 원장 쿼리는 ORM에 끌려다니지 않아야 한다.
- 프론트엔드는 조회/보고와 입력/편집을 분리해서 생각한다.

## 1차 목표에 맞는 스택 기준

1차에서 가장 중요한 것은 아래다.

- 초기 개발 속도
- 낮은 보일러플레이트
- fixture 기반 TDD 연결 용이성
- 원장/분개 로직을 빠르게 검증할 수 있는 구조

이 기준에서는 “큰 프레임워크의 완성도”보다 “가볍게 시작할 수 있는가”가 더 중요하다.

## 2차 목표에 맞는 스택 기준

2차에서 중요한 것은 아래다.

- 정교한 SQL과 집계
- 멀티테넌시 확장
- 배치/결산/평가 작업 확장
- 권한/감사/운영 기능 확장

이 기준에서는 단순 CRUD 생산성보다 `쿼리 통제력`과 `레이어 분리`가 중요하다.

## 마이그레이션 가능성 기준

아래 조건을 만족해야 다음 스택으로 옮기기 쉽다.

- HTTP 레이어와 도메인 로직이 분리돼 있다.
- repository 인터페이스가 DB 접근을 감춘다.
- 스키마 정의가 문서와 fixture에 의해 검증된다.
- 테스트가 프레임워크가 아니라 시나리오 기반이다.
- 인증/권한/배치가 특정 프레임워크 API에 과하게 박혀 있지 않다.

## 백엔드 프레임워크 비교

### Fastify

성격:

- 가볍고 빠른 웹 서버 프레임워크

장점:

- 초기 보일러플레이트가 적다
- 응답 속도와 단순성이 좋다
- 회계 엔진을 프레임워크 바깥에서 설계하기 좋다

단점:

- 구조를 팀이 직접 잡아야 한다
- 규칙 없이 확장하면 빠르게 무거워질 수 있다

적합성:

- 1차 MVP에 가장 잘 맞는다

### NestJS

성격:

- 구조 강제력이 큰 엔터프라이즈 지향 Node 프레임워크

장점:

- 모듈화와 DI가 강하다
- 중장기 구조 통제에 유리하다
- 인증, 배치, 권한, 모듈 분리에 유리하다

단점:

- 초기 보일러플레이트가 크다
- 팀이 Nest 구조를 충분히 이해하지 못하면 무거워질 수 있다
- MVP 속도 기준에서는 과할 수 있다

적합성:

- 2차 이후 구조 고도화에는 좋지만, 1차 목표에는 다소 무겁다

### Hono 또는 Express 계열

성격:

- 매우 단순한 HTTP 레이어

장점:

- 시작 속도가 매우 빠르다
- 학습 비용이 낮다

단점:

- 프로젝트가 커질수록 구조 일관성을 직접 유지해야 한다

적합성:

- 소규모 MVP에는 가능
- 이 프로젝트는 회계 도메인 복잡도가 있어 Fastify가 더 무난하다

## DB 접근 스택 비교

### Drizzle

장점:

- SQL과 매우 가깝다
- 타입 안정성이 좋다
- 정교한 쿼리와 정규화된 스키마에 잘 맞는다
- 회계/원장 중심 도메인에 적합하다

단점:

- SQL 이해가 더 많이 필요하다

적합성:

- 1차와 2차를 동시에 만족시키기 가장 좋다

### Prisma

장점:

- 생산성이 높다
- 스키마와 클라이언트 경험이 좋다
- 팀 협업 진입장벽이 낮다

단점:

- 원장성 집계와 세밀한 SQL 통제에서는 Drizzle보다 답답할 수 있다

적합성:

- 빠른 CRUD 제품에는 좋다
- 이 프로젝트에선 핵심 집계 구간에서 raw SQL 의존이 커질 수 있다

### TypeORM

장점:

- 전통적인 ORM 패턴에 익숙한 팀은 쉽게 접근할 수 있다

단점:

- 엔티티 중심 모델이 회계 이력/원장 중심 도메인과 꼭 잘 맞지 않는다
- 이 프로젝트에선 추상화가 오히려 부담이 될 수 있다

적합성:

- 셋 중 우선순위가 가장 낮다

## 프론트엔드 스택 비교

### Next.js

장점:

- 하이브리드 렌더링 가능
- 조회/보고 화면과 입력 화면을 함께 다루기 좋다
- SaaS에서 권한 기반 초기 화면 구성에 유리하다

단점:

- 단순 SPA보다 구조가 무거울 수 있다

적합성:

- 범용 SaaS + 보고/조회 요구가 있으므로 유효하다

### Vite + React SPA

장점:

- 가장 가볍게 시작할 수 있다
- 개발 경험이 빠르다

단점:

- SSR/초기 권한 처리/초기 데이터 조합은 직접 더 챙겨야 한다

적합성:

- 1차 MVP만 보면 매우 좋다
- 다만 외부 SaaS와 보고 초기화까지 보면 Next.js가 더 안정적이다

## 현재 권장안

### 1차 권장 스택

- 백엔드: `Fastify + TypeScript`
- DB: `PostgreSQL`
- DB 접근: `Drizzle`
- 프론트엔드: `Next.js + React`
- 상태/폼: `TanStack Query`, `React Hook Form`
- 배치/큐: 없음

이유:

- MVP를 가장 빠르고 가볍게 시작할 수 있다
- 회계 엔진은 별도 도메인 계층으로 분리 가능하다
- Drizzle 덕분에 정교한 쿼리 확장성이 유지된다
- Next.js는 외부 SaaS와 보고형 화면에 유리하다

### 2차 확장 스택

- 백엔드: `Fastify` 유지 또는 `NestJS`로 재조직
- DB: `PostgreSQL` 유지
- DB 접근: `Drizzle + SQL projection 강화`
- 배치/큐: `Redis + BullMQ` 또는 `Temporal`
- 분석/운영: 별도 reporting layer 추가 검토

## 마이그레이션 친화적 구조

아래를 지키면 Fastify에서 NestJS로 가는 것도 어렵지 않다.

- `apps/api`에는 HTTP 라우트만 둔다
- `packages/domain`에는 회계 규칙과 유스케이스를 둔다
- `packages/db`에는 Drizzle 스키마와 repository 구현을 둔다
- `packages/test-fixtures`에는 scenario loader와 기대값 검증 로직을 둔다

즉, 프레임워크를 바꿔도 아래는 유지된다.

- fixture
- schema
- domain use case
- journal rules
- repository interface

## 지금 시점의 추천 결론

- 1차는 `Fastify + Drizzle + PostgreSQL + Next.js`
- NestJS는 지금 고정하지 않는다
- 다만 구조는 나중에 NestJS로 이동할 수 있게 계층 분리를 강하게 가져간다
