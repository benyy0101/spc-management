# TDD용 예시 데이터 세트 전략

## 목적

이 문서는 SPC 구조 금융상품 회계 시스템을 TDD 방식으로 개발하기 위해, 어떤 예시 데이터 세트를 먼저 만들어야 하는지 정의한다.

이 프로젝트에서는 테스트 코드보다 먼저 `시나리오`, `입력 데이터`, `기대 분개`, `기대 원장`, `기대 재무제표`를 정의하는 것이 맞다.

## 왜 예시 데이터 세트가 먼저여야 하는가

이 시스템의 핵심은 화면이 아니라 숫자의 정확성이다. 따라서 기능 정의도 다음 질문으로 검증해야 한다.

- 어떤 입력 거래가 들어오는가
- 어떤 계약 조건이 적용되는가
- 어떤 분개가 생성돼야 하는가
- 기준일에 어떤 잔액이 남아야 하는가
- 결산 후 어떤 재무제표가 나와야 하는가
- 투자자에게 어떻게 배분돼야 하는가

즉, 예시 데이터 세트는 단순 샘플 데이터가 아니라 도메인 정답지다.

## 데이터 세트 설계 원칙

- 하나의 세트는 하나의 핵심 시나리오를 검증해야 한다.
- 각 세트는 회계주체를 명확히 구분해야 한다.
- 계약 속성과 이벤트 시점이 반드시 포함돼야 한다.
- 기대 결과는 최소 분개, 원장, 재무제표, 투자자 배분까지 포함해야 한다.
- 반례와 오류 시나리오도 포함해야 한다.
- 1차 투자자 배분 규칙은 `단순 지분율(pro-rata)`을 기준으로 한다.
- 1차 현금흐름표는 `간접법`을 기준으로 한다.
- 기준 운영통화는 `USD`이며, 보고 결과는 `KRW` 병행 산출을 포함할 수 있어야 한다.

## 이번 프로젝트의 테스트 기준 결정

### 투자자 배분 기준

- 1차 기준은 단순 지분율 배분으로 한다.
- 이유:
  - 회계 엔진과 배분 엔진의 기본 연결을 먼저 검증하는 것이 우선이다.
  - 클래스별 우선순위, hurdle, carry는 별도 규칙군으로 복잡도가 크게 증가한다.
  - 초기부터 복합 배분을 넣으면 회계 오류와 배분 오류를 분리하기 어려워진다.

확장 방향:

- 2차에서 클래스 구조
- 우선/후순위 배분
- hurdle
- carry

### 현금흐름표 기준

- 1차 기준은 간접법으로 한다.
- 이유:
  - 원장, 손익, 재무상태표 사이의 연결 정합성을 먼저 검증하기에 적합하다.
  - 결산 로직 검증과 잘 맞는다.
  - 직접법은 현금 이벤트 분류 체계가 더 정교하게 필요하므로 후속 고도화가 적절하다.

확장 방향:

- 2차에서 직접법 또는 병행 지원 검토

### 통화 기준

- 운영 기준 통화는 USD다.
- 보고 산출은 USD를 기본으로 하고, KRW 환산 결과도 기대값에 포함한다.
- 이유:
  - 외화 구조를 후반에 붙이면 원장과 보고 로직 수정 범위가 커진다.
  - 초기 fixture부터 USD와 KRW 병행 결과를 같이 검증하는 편이 안전하다.

## 데이터 세트의 최소 구성

각 예시 데이터 세트는 아래 구조를 가진다.

### 1. 시나리오 메타 정보

- 시나리오 ID
- 시나리오 이름
- 검증 대상 기능
- 회계 기준
- 기준 통화
- 대상 회계주체

### 2. 마스터 데이터

- 법인
- SPC
- 펀드
- 투자자
- 상품
- 계정과목
- 차원
- 계약
- 환율

### 3. 이벤트 입력

- 거래일
- 회계일
- 결제일
- 이벤트 유형
- 금액
- 통화
- 관련 계약 ID

### 4. 기대 결과

- 기대 분개
- 기대 계정별 잔액
- 기대 상품별 잔액
- 기대 투자자별 배분
- 기대 BS
- 기대 PL
- 기대 CF

### 5. 예외 또는 검증 포인트

- 마감 후 수정 여부
- 외화 환산 영향
- 평가손익과 실현손익 구분
- 수기분개 필요 여부

## 반드시 먼저 만들어야 하는 핵심 세트

### 세트 1. 투자자 출자와 펀드 설정

목적:

- 투자자 납입
- 펀드 자본 인식
- 투자자 지분 구조 검증

검증 포인트:

- 투자자별 출자금 반영
- 펀드 장부와 투자자 배분 정보 분리

### 세트 2. 펀드의 SPC 출자

목적:

- 펀드가 SPC에 자금을 투입하는 흐름 검증
- 펀드 장부와 SPC 장부를 구분 검증

검증 포인트:

- 동일 사건의 회계주체별 분개 차이

### 세트 3. SPC의 자산 취득

목적:

- 선박 관련 자산 취득 또는 대출채권 취득 검증

검증 포인트:

- 취득원가 인식
- 현금 감소
- 자산 장부가 설정

### 세트 4. 차입 실행

목적:

- 선순위 또는 일반 차입 발생 검증

검증 포인트:

- 부채 인식
- 차입금과 현금 증가
- 차입 주체 확인

### 세트 5. 월말 이자 accrual

목적:

- 이자 발생과 현금 미수취 상황 검증

검증 포인트:

- 미수수익
- 이자수익
- 발생주의 반영

### 세트 6. 이자 실제 수취

목적:

- 현금 유입과 미수수익 해소 검증

검증 포인트:

- 현금 증가
- 미수수익 감소
- 손익 중복 인식 방지

### 세트 7. 원금 일부 상환

목적:

- 원금 감소와 잔액 재계산 검증

검증 포인트:

- 채권 또는 대출 원금 감소
- 현금 증가
- 이후 이자 계산 기준 변경

### 세트 8. 평가손익 반영

목적:

- 공정가치 또는 평가 조정 검증

검증 포인트:

- 평가손익 계정 반영
- 실현손익과 분리

### 세트 9. 손상 반영

목적:

- 연체 또는 회수 가능성 저하 상황 검증

검증 포인트:

- 대손충당금 설정
- 장부가 조정

### 세트 10. 외화 환산

목적:

- USD 기준 운영과 타 통화 거래 혼재 검증

검증 포인트:

- 환율 적용일
- 환산손익 반영
- 보고통화 산출

### 세트 11. 캐시 워터폴 배분

목적:

- 유입 현금의 우선순위 배분 검증

검증 포인트:

- 비용
- 이자
- 원금
- 준비금
- 투자자 분배 순서

### 세트 12. 월말 결산과 재무제표

목적:

- 월마감 이후 BS, PL, CF 생성 검증

검증 포인트:

- 수정분개 반영
- 기준일 잔액 일치
- 보고서 간 정합성

### 세트 13. 투자자 배분

목적:

- 투자자별 손익 및 현금 배분 검증

검증 포인트:

- 지분율 기준 배분
- 투자자별 배분표
- 펀드 총액과 투자자 합계 일치

## TDD 작성 순서

권장 순서는 다음과 같다.

1. 세트 1~4로 장부 생성 구조를 먼저 검증한다.
2. 세트 5~7로 accrual과 상환을 검증한다.
3. 세트 12로 재무제표 산출을 검증한다.
4. 세트 13으로 투자자 배분을 검증한다.
5. 세트 8~11로 평가, 손상, 외화, 워터폴을 확장한다.

## 테스트 레벨 권장 구조

### 레벨 1. 분개 규칙 테스트

- 입력 이벤트 1건
- 기대 분개 n건

### 레벨 2. 원장 집계 테스트

- 이벤트 묶음
- 기대 계정 잔액
- 기대 보조원장 잔액

### 레벨 3. 결산 테스트

- 월말 이벤트 세트
- 기대 수정분개
- 기대 시산표

### 레벨 4. 보고 테스트

- 기대 BS
- 기대 PL
- 기대 CF
- 기대 투자자 배분표

## 구현 전에 꼭 확인할 질문

1. 예시 데이터의 정답은 누가 승인할 것인가
2. 일반기업회계기준상 내부 정책 차이가 있는 항목은 무엇인지
3. 외화 보고는 USD 기본에 KRW 병행으로 충분한지
4. 클래스별 우선순위 배분을 2차 범위로 두는지

## 결론

예시 데이터 세트를 먼저 만드는 접근은 맞다. 오히려 이 프로젝트에서는 권장사항이 아니라 사실상 필수다.

화면이나 API보다 먼저 아래를 확정하는 것이 좋다.

- 핵심 시나리오 12~13개
- 각 시나리오의 계약과 이벤트 데이터
- 기대 분개
- 기대 잔액
- 기대 재무제표
- 기대 투자자 배분 결과
